# Errors & incidents

Real problems hit while building this project, why they happened, and how they were fixed. Grouped roughly by phase/area. The point of keeping this isn't just a changelog — several of these are the kind of mistake that's easy to repeat in a different file six months from now, so the "why" and "lesson" lines matter more than the fix itself.

---

## Backend / data layer

### Datetime timezone mismatch on session/token columns

**What happened:** `asyncpg` raised a `TypeError` when writing to `sessions.expires_at` and similar columns.

**Why:** The columns were created as Postgres `TIMESTAMP WITHOUT TIME ZONE`, but the app consistently builds tz-aware `datetime` objects (`datetime.now(timezone.utc)`). asyncpg refuses to silently drop the tz info.

**Fix:** Added `DateTime(timezone=True)` to every datetime column in `backend/app/models.py`, then migrated the schema to `timestamptz`.

**Lesson:** Decide "naive vs aware" once, globally, at the start of a project — not per-column as each one gets written. This codebase's rule is: always tz-aware, always UTC, always `timestamptz` in Postgres.

### Alembic autogenerate silently skipped a type-only migration

**What happened:** After fixing the above, `alembic revision --autogenerate` produced a migration with an empty `upgrade()` — the `TIMESTAMP` → `TIMESTAMPTZ` change wasn't detected at all.

**Why:** Alembic's autogenerate does not compare column *types* by default — only presence/absence of columns, tables, indexes, etc. `compare_type` defaults to off.

**Fix:** Added `compare_type=True` to both `context.configure()` calls in `backend/migrations/env.py`. Since only dev/test data existed at the time, migration history was reset (downgrade to base, regenerate a single fresh "initial schema" migration) rather than patching history.

**Lesson:** Never trust an autogenerated migration by inspection of "did it run without error" — read the generated file's actual diff before applying it. This one *looked* successful (exit code 0, file created) while doing nothing.

### Missing `email-validator` dependency

**What happened:** App crashed on import/startup once `EmailStr` fields were added to `schemas.py`.

**Why:** Pydantic's `EmailStr` type requires the separate `email-validator` package at runtime; it's not pulled in automatically by `pydantic`.

**Fix:** Added `email-validator` to `requirements.txt`.

### Gitea 403 on repo creation

**What happened:** `POST /projects` failed when trying to create the per-project Gitea repo, with a 403 from Gitea's API.

**Why:** The admin token used by the backend was generated with only the `write:repository` scope. Creating a repo *under an organization* (this project uses a fixed `projects` org for all per-project repos) additionally requires `write:organization`.

**Fix:** Regenerated the Gitea token with both `write:repository` and `write:organization` scopes. `infra/PHASE2-RUNBOOK.md` now calls out both explicitly so this doesn't get rediscovered later.

### Stale `.env` values surviving `uvicorn --reload`

**What happened:** After editing `.env` (e.g. `DATABASE_URL`, `GITEA_ADMIN_TOKEN`), the running backend kept using the *old* value even though the file had changed and uvicorn's reloader had clearly fired.

**Why:** `uvicorn --reload` watches source files and restarts the worker process on change, but `.env` is loaded once at process start via `pydantic-settings`. A file-watch-triggered reload does not re-read `.env` from scratch the way a fresh `uvicorn app.main:app` invocation does.

**Fix:** No code fix — just discipline: after any `.env` change, fully stop and restart uvicorn rather than relying on the auto-reload.

**Lesson:** Config loaded once into a `Settings` object at import time will always have this failure mode. Worth remembering if this ever moves to a hot-reloadable config source.

## Security

### Path traversal — allowlist vs blocklist, and a second gap in the Gitea client

**What happened:** While reviewing path-traversal defenses (`is_safe_project_path`) against a deliberately adversarial mid-path `../../` case, the existing check held up under test — but the investigation surfaced two real, separate gaps:
1. The original check was a **blocklist** (reject strings containing `..`), which misses backslashes, percent-encoded traversal sequences, and other URL-special characters depending on how the string is later interpreted.
2. Even a path that *did* pass validation was then interpolated unencoded into Gitea API request URLs in `gitea_client.py` — a second, independent place the same class of bug could reappear if the validator were ever bypassed or a new caller forgot to invoke it.

**Fix:** Rewrote `backend/app/utils/paths.py` from a blocklist to an **allowlist**: `posixpath.normpath` the input, reject anything that still starts with `..`, and require every path segment to match `^[A-Za-z0-9_.-]+$`. Separately, added `urllib.parse.quote(segment, safe="")` per path segment in `gitea_client.py` before building request URLs — defense in depth, so the URL-construction layer is safe even if a caller upstream forgot to validate.

**Lesson:** Blocklists enumerate the attacks you've thought of; allowlists enumerate what's actually valid. For anything that becomes a filesystem path or a URL segment, prefer allowlisting the character set outright. Also: a validator in one place doesn't mean every downstream consumer of that value is safe — check each place untrusted data gets interpolated into something structural (a URL, a shell command, a path), not just the one entry point.

### Exposed API key in conversation context

**What happened:** The user's real Anthropic API key was inadvertently read into the assistant's context via an IDE auto-read event on a local `apikey.json` file.

**Why:** An editor/IDE integration surfaced the file's contents automatically, not as a result of any explicit request to read a secrets file.

**Fix:** No code change. The key was not echoed or repeated back in any form; the user was told to delete the file and consider the key compromised (rotate it on Anthropic's console).

**Lesson — standing rule:** Never echo, repeat, or reprint a secret that lands in context, regardless of how it got there. Always recommend deletion/rotation when a secret is accidentally exposed, treating it as compromised even if the exposure was purely local/accidental.

### CSRF: why double-submit token instead of `SameSite=strict` alone

**Not a bug — a design decision worth recording since it was debated.** `overview.md`'s Phase 3 notes floated `SameSite=strict` alone as sufficient. When it came time to implement, the simpler option was proposed first; the user pushed back and asked for the more rigorous, "real life scenario" choice instead.

**Why the stronger option won:** `SameSite=strict` stops a cross-site *request* from carrying this site's cookies at all, which covers most CSRF — but it has known gaps (e.g. top-level navigations from external links in some browser/version combinations, and it offers no protection if `SameSite` handling is ever weakened for compatibility reasons). A double-submit CSRF token doesn't rely on browser cookie-policy enforcement being correct or unchanged — the server independently verifies that whoever made the request could read a value that only same-origin JS can read.

**Implementation:** `backend/app/security/csrf.py` — a non-httpOnly `csrf_token` cookie plus a required `X-CSRF-Token` header on every state-changing route, compared with `secrets.compare_digest`. The frontend (`frontend/lib/api.ts`) reads the cookie and attaches the header automatically for `POST`/`PUT`/`PATCH`/`DELETE`.

**Lesson:** When a security control has a "simple" and a "rigorous" option and the two cost roughly the same to implement, default to the rigorous one rather than the one that merely passes the obvious test cases.

## Frontend

### Illegible chat text (white text on light background)

**What happened:** Chat bubbles were unreadable — pale text on a pale background — despite the CSS looking correct in the source.

**Why:** `app/globals.css` had `create-next-app`'s default `@media (prefers-color-scheme: dark)` block, which auto-swapped text/background colors based on OS theme — but the rest of the app's components were never designed with a dark variant, so the swap produced a broken combination rather than an intentional dark mode.

**Fix:** Removed the dark-mode auto-switch block from `globals.css` entirely, since this app doesn't have a real dark theme (yet).

### Subpage navigation stuck "loading" in the live preview

**What happened:** Clicking an in-page link (e.g. to a second generated page like `about.html`) inside the live preview did nothing / hung. Notably, the AI chatbot itself had already tried to fix this on request — first by generating hash-based routing, then by removing it — without success.

**Why:** The preview renders via `<iframe srcDoc={html}>`, which has **no server behind it**. A real deployed site can resolve a relative link to another file; a `srcDoc` iframe is just one static HTML string with no backing filesystem or HTTP server, so `<a href="about.html">` has nothing to navigate to. This is architectural, not something fixable by changing the generated page's own code/markup — which is why the AI's own attempts (operating only on the generated HTML) couldn't succeed.

**Fix:** `frontend/lib/preview.ts` injects a click-interceptor script into the rendered HTML that turns local link clicks into a `postMessage({type: "preview-navigate", path})` to the parent window instead of a real navigation; `components/PreviewFrame.tsx` listens for that message and re-renders the iframe with the requested page's content substituted in as the new entry point.

**Lesson:** Some bugs live in the harness around the AI-generated content, not in the content itself — no amount of re-prompting the model fixes a sandboxing/architecture constraint it has no visibility into or control over.

### Chat history and preview lost on page reload

**What happened:** Reloading a project's workspace page reset the chat panel and preview to empty, even though the conversation and previously-proposed files still existed server-side (confirmed via Postgres/Gitea) and just weren't being fetched back.

**Why:** `projects/[id]/page.tsx` only ever built `turns` and `files` state from live `/chat` responses — there was no code path that reconstructed that state from history on mount.

**Fix:** Added `GET /projects/{id}/messages` on the backend (`backend/app/routers/chat.py`) returning stored messages in order. On the frontend, a `useEffect` on mount fetches this and replays it: each stored assistant message's `content` is the same raw JSON shape (`{reply, files}`) a live response has, so the same `mergeProposedFiles` merge logic used for live chat turns rebuilds the accumulated file map from history, with a `try/catch` fallback per-row so one unparseable historical row can't break loading the rest.

**Lesson:** Reuse the same merge/reducer logic for "replaying history" and "handling a live update" rather than writing a parallel reconstruction path — they're the same operation applied to a list of the same-shaped objects, and keeping them in sync by construction avoids the two silently drifting apart later.

### `FormEvent` generic type warning across form pages

**What happened:** TypeScript flagged bare `FormEvent` (no generic parameter) as deprecated across `login`, `register`, `dashboard`, `api-keys`, and the project workspace page. Not a build error (`tsc --noEmit` was clean) — a deprecation warning.

**Fix:** Changed each to `FormEvent<HTMLFormElement>`, the properly-typed form applied to `onSubmit` handlers.

## Infra

### LocalStack IAM/STS enforcement doesn't work locally (known, not "fixed")

**What happened:** Least-privilege IAM policies and STS `AssumeRole` wiring were written correctly in Terraform (Phase 1), but LocalStack's local enforcement of IAM restrictions doesn't actually block anything — a role scoped to only `kms:Decrypt` can still, in practice, do more than that against LocalStack.

**Why:** Confirmed to match a known upstream LocalStack limitation ([localstack/localstack#7183](https://github.com/localstack/localstack/issues/7183)), not a mistake in this project's Terraform.

**Status:** Left as-is and documented rather than worked around. Verification for this piece stops at "the Terraform policy/role/trust-policy is written correctly," not "the emulator proved it's enforced" — that gap only closes once this points at real AWS IAM.
